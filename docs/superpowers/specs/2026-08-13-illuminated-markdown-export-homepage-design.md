# Illuminated Markdown Export and Homepage Design

## Goal

Reframe the public exhibition as a prophecy told in six movements, add a dependable `export.md` edition of all twenty-two chapters of Revelation with all ninety artworks placed exactly once, and make the homepage feel like the opening spread of a premium illuminated book.

The export is the editable source for later DOCX, EPUB, PDF, Google Docs, and print-production work. It must remain generated from the same canonical scripture and scene metadata as the website rather than becoming a second content source.

## Success criteria

- Public interface copy calls the complete work “a prophecy in six movements” and each of the six top-level works “Movement I” through “Movement VI.”
- Existing `/tapestries/...` and `/embed/tapestries/...` URLs, query parameters, scene IDs, JSON keys, and internal TypeScript names remain stable.
- Exact World English Bible text and canonical artwork titles remain unchanged, including legitimate uses of “vision” inside scripture or titles.
- `/export.md` downloads a complete, readable Markdown book containing 22 sequential chapters, all 404 canonical verses with `chapter:verse` numbering, and all 90 unique artworks exactly once.
- Image links are absolute: the local asset-server origin during local work and the configured R2 custom domain in production.
- The homepage gains a distinctive illuminated-ledger presentation without a new runtime dependency, carousel, or client-side export generator.
- The repository explains how to convert the Markdown to DOCX, EPUB, and PDF with Pandoc and how to open the DOCX in Google Docs.

## Terminology policy

The rename applies to public taxonomy and editorial prose:

- Homepage: “A prophecy in six movements” and “The six movements.”
- Primary navigation: “Movements.”
- Exhibition pages and metadata: “Movement I,” “Movement II,” and so on.
- Pagination and accessibility labels: “Previous movement,” “All movements,” “Movement navigation,” and “Movement I scenes.”
- Revelation index and chapter navigation: refer to the six movements.
- Narrative summaries generated by `scripts/generate-content.mjs`: replace editorial uses of “tapestry” with “movement,” and replace taxonomy-level uses of “vision” with natural wording such as “prophecy,” “revelation,” or “narrative.”

The rename does not alter internal implementation vocabulary. `Tapestry`, `allTapestries`, `getTapestry()`, CSS class names, route directories, `content/tapestries.json`, source-vault directory names, release object keys, and scene IDs remain unchanged. Canonical artwork titles such as “Vision of the Seven Candlesticks” and exact scripture phrases such as “horses in the vision” also remain unchanged.

The four- or five-part explanatory outline currently stored in each top-level object’s `movements` array is a narrative subdivision, not another layer of top-level movements. Its public eyebrow becomes “The prophecy unfolds” to avoid ambiguous nested terminology; its internal field name remains unchanged.

## Export architecture

### Pure book renderer

`lib/markdown-book.ts` accepts the canonical chapter array, canonical scene array, and an absolute asset origin, then returns the full Markdown string. It has no browser, filesystem, React, or Next.js dependency, which makes its behavior directly testable.

The renderer reads scripture only from `content/revelation.web.json`. It does not assemble the book from each scene’s copied `passages`, because doing so would repeat verses wherever scene spans overlap.

### Static route

`app/export.md/route.ts` exposes the renderer through a request-independent `GET` response. Next.js 16 can prerender this route to `out/export.md` under the existing `output: "export"` configuration. The response uses `text/markdown; charset=utf-8`; the homepage link uses the native `download` attribute and displays the exact label `export.md`.

The route obtains the asset origin from `NEXT_PUBLIC_ASSET_BASE_URL`. When that value is absent outside a production Vercel build, it uses `http://127.0.0.1:3101`, matching `npm run dev:local`. Production retains the existing requirement for a clean HTTPS R2 custom domain. `scripts/serve-static.mjs` recognizes `.md` as Markdown so a locally built static site serves the correct media type.

### Why this approach

A static route keeps the export synchronized with every build and avoids a committed generated book that can drift. It also avoids shipping the complete scripture and scene manifests into a client-side Blob generator. No new package is required.

## Markdown book structure

The document uses broadly portable Markdown and a small Pandoc-compatible YAML metadata block:

1. Title, subtitle, creator, language, and rights metadata.
2. A visible title page with “The Revelation to John” and “An illuminated prophecy in six movements.”
3. A brief edition note naming the World English Bible and the artwork license.
4. Twenty-two level-two chapter headings, one for each chapter in order.
5. One paragraph per canonical verse, beginning with a bold `chapter:verse` marker.
6. Figures placed directly before the first verse mapped to each scene.

Each figure uses the scene’s `reader` rendition because it is document-sized and served inline, unlike archival originals that currently carry attachment headers. The Markdown includes:

- Descriptive alt text.
- The absolute reader-image URL.
- Scene ID, title, movement number, and full scripture reference.
- Artwork attribution and CC BY-SA 4.0 notice.

The export preserves exact canonical verse text. It does not add red-letter formatting, page-break directives, raw layout HTML, or print-specific sizing in this first edition; those concerns belong in a later Pandoc reference DOCX or EPUB stylesheet.

## Artwork placement and uniqueness

For each scene, the placement anchor is the first `scriptureSpans` entry’s `startChapter` and `startVerse`. The renderer indexes all scenes by that anchor while preserving `allScenes` order. It then walks chapters and verses in canonical order, emitting every figure at an anchor immediately before the corresponding verse.

Several anchors intentionally hold two or three scenes. Those scenes appear together in canonical order. Multi-span scenes appear only at their first span. A set of emitted scene IDs prevents duplication and makes accidental repeated figures a build failure.

The renderer rejects output unless all of the following hold:

- Chapters are numbered 1 through 22 with no gap.
- All 404 canonical verses are emitted once in chapter and verse order.
- Exactly 90 unique scene IDs are emitted.
- Exactly 90 unique reader-image URLs are emitted.
- Every image URL is absolute HTTP or HTTPS; relative and `file:` references are rejected.
- Every scene has a valid first scripture anchor present in the canonical text.

The local Markdown therefore depends on `npm run dev:local` remaining active while Pandoc downloads its images. The production Markdown depends on the immutable R2 URLs. Pandoc embeds those downloaded images into DOCX and EPUB, making the converted artifacts self-contained.

## Homepage direction: illuminated ledger

The homepage remains a Server Component. The overhaul uses the existing content objects and artwork renderer; it does not introduce a carousel, animation library, or new state.

### Hero

The opening becomes an editorial two-column spread. The text column contains the Revelation eyebrow, “A prophecy in six movements,” a tightened description, primary reading actions, and a restrained ledger of facts: 6 movements, 22 chapters, and 90 illuminations. The visual column features `T6-B03`, “New Jerusalem,” framed with fine gold rules, layered borders, and quiet captioning to establish the illuminated-book tone immediately.

### Movement index

The six existing rows become an illuminated ledger. Each row retains its Roman numeral, title, and concise summary, while gaining its movement’s lead artwork and a clearer “Enter Movement” cue. Desktop presentation alternates generous editorial text with contained artwork; mobile presentation becomes a single readable column. Artwork remains uncropped with `object-fit: contain`.

### Archive and export callout

The archive section becomes a colophon-like closing spread. It distinguishes three actions:

- `export.md` for the complete illuminated scripture edition.
- Download artwork v1 for the archival original release.
- Fork the source for the repository.

The export description states that the Markdown contains 22 chapters and 90 unique linked images and is ready for Pandoc conversion.

### Interaction and accessibility

Hover and focus states use subtle rule, color, and transform changes. All meaningful content remains visible without hover. Keyboard focus remains explicit, artwork alt text remains canonical, target sizes remain accessible, and `prefers-reduced-motion` disables decorative transitions. The work uses an `app/page.module.css` stylesheet so the overhaul does not leak into the reader or movement pages.

## Conversion guide

`docs/book-export.md` covers this workflow:

1. Install Pandoc on macOS with `brew install pandoc` or use an existing Pandoc installation.
2. For a locally downloaded export, run `npm run dev:local` and keep it running during conversion so the localhost image URLs remain reachable.
3. Create DOCX:

   ```bash
   pandoc export.md --from=gfm+yaml_metadata_block --standalone --toc -o revelations.docx
   ```

4. Create EPUB:

   ```bash
   pandoc export.md --from=gfm+yaml_metadata_block --standalone --toc --split-level=2 -o revelations.epub
   ```

5. Create PDF when a Pandoc-compatible PDF engine is installed:

   ```bash
   pandoc export.md --from=gfm+yaml_metadata_block --standalone --toc -o revelations.pdf
   ```

6. For the dependable Google Docs path, upload `revelations.docx` to Google Drive and open it with Google Docs. From Google Docs, edit normally or choose File → Download → PDF Document. Direct Markdown import remains documented as a text-focused convenience rather than the reliable image-preserving route.

The guide notes that a production/R2 export can be converted without running the local asset server, as long as the converter can access the public image URLs.

## Error handling

Content and URL errors fail deterministically during tests and the static build, before a broken book can be published. Errors name the missing chapter, verse, scene, duplicate ID, duplicate URL, or invalid origin. Expected multi-scene anchor collisions are not errors.

Homepage image failures continue to use the project’s existing descriptive fallback. The export itself cannot embed fallback art; a failed HTTP fetch remains visible to Pandoc, and the conversion guide instructs the user to keep the local server running or use the production export.

## Testing and verification

Automated coverage will prove observable behavior rather than source wording alone:

- Renderer test using canonical data: 22 chapter headings, 404 unique numbered verses, 90 unique scene markers, and 90 unique absolute image URLs.
- Placement tests: figures appear before their first mapped verse; multi-span scenes and shared anchors do not duplicate or reorder artwork.
- Validation tests: relative origins, invalid anchors, duplicate scenes, and incomplete chapter data fail with useful messages.
- Route/build test: `export.md` is emitted by the static build with Markdown content.
- Homepage browser tests: approved terminology, the `export.md` download target, six movement entries, responsive containment, keyboard focus, and reduced-motion behavior.
- Full verification: unit tests, content validation, Next.js production build, and targeted desktop/mobile Playwright checks.
- Visual QA: inspect the rendered homepage at desktop and mobile widths and inspect the generated Markdown plus at least one Pandoc DOCX conversion when Pandoc is available locally.

## Non-goals

- Renaming routes, JSON files, scene IDs, internal TypeScript symbols, or source-vault folders.
- Shipping a ZIP containing Markdown plus local images.
- Generating DOCX, EPUB, or PDF on the website.
- Designing final print typography, trim size, bleed, imposition, or a custom reference DOCX/EPUB stylesheet.
- Moving the artwork to R2 as part of this change.
- Rewriting scripture or canonical artwork titles.
